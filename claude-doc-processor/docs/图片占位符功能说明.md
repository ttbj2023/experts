# DOCX 转 Markdown - 图片占位符功能说明

## 更新概述

### 优化内容
优化了 `convert_docx_to_markdown_v2.py` 脚本，解决了图片信息丢失的问题。GLM 模型现在会在识别时使用**图片占位符**标记图片位置，确保图片不会丢失。

### 更新的文件
1. **scripts/process_pdf_with_glm46v_v2.py** - 更新提示词（v4版本）
2. **scripts/convert_docx_to_markdown_v2.py** - 优化图片嵌入逻辑

## 功能说明

### 工作原理

```
DOCX 文件
    ↓
1. 提取图片 → 保存到 images/ 目录
    ↓
2. 转换为 PDF → LibreOffice
    ↓
3. PDF 转 Markdown → GLM-4.6V-Flash（生成图片占位符）
    ↓
4. 匹配与替换 → 将占位符替换为实际图片引用
    ↓
最终 Markdown（图片位置准确 + 图片描述）
```

### 图片占位符格式

GLM 模型会在 Markdown 中生成如下格式的占位符：

```html
<!-- IMAGE_PLACEHOLDER
type: 几何图形
description: 直角三角形ABC，直角在C点，边长AB=5cm，BC=3cm，AC=4cm
-->
```

**占位符包含：**
- `type`: 图片类型（几何图形、函数图像、统计图表、示意图等）
- `description`: 详细描述图片内容，便于后续匹配

### 占位符示例

#### 1. 几何图形
```html
<!-- IMAGE_PLACEHOLDER
type: 几何图形
description: 直角三角形ABC，直角在C点，边长AB=5cm，BC=3cm，AC=4cm，标注有角度∠A=53.13°
-->
```

#### 2. 函数图像
```html
<!-- IMAGE_PLACEHOLDER
type: 函数图像
description: 直角坐标系，绘制函数y=x²的抛物线，经过点(0,0)、(1,1)、(2,4)、(-1,1)、(-2,4)
-->
```

#### 3. 统计图表
```html
<!-- IMAGE_PLACEHOLDER
type: 统计图表
description: 柱状图，横轴显示"一班、二班、三班"，纵轴显示人数，数据分别为45、52、38人
-->
```

**替换后的效果**：

上述占位符会被替换为：
```markdown
![几何图形](images/image1.png)
```
或
```markdown
![函数图像](images/image2.png)
```
或
```markdown
![统计图表](images/image3.png)
```

**注意**：长描述仅用于匹配和日志，最终文档中只保留简洁的图片类型标签。

## 使用方法

### 基本用法

```bash
# 转换单个 DOCX 文件（启用图片占位符）
python3 scripts/convert_docx_to_markdown_v2.py input.docx

# 指定输出目录
python3 scripts/convert_docx_to_markdown_v2.py input.docx -o output_dir

# 禁用 AI 分析（保留所有图片，不使用占位符）
python3 scripts/convert_docx_to_markdown_v2.py input.docx --no-analyze
```

### 输出结构

```
output_docx_to_md_v2/
├── document.md              # 最终 Markdown 文件（图片已嵌入）
├── images/                  # 图片目录
│   ├── image1.png
│   ├── image2.jpg
│   └── ...
└── meta.json                # 转换统计信息
```

## 智能匹配逻辑

### 占位符匹配模式（唯一模式）

**必需条件**：
- GLM-4.6V-Flash 必须生成图片占位符
- 使用 v4 版本提示词（`process_pdf_with_glm46v_v2.py`）

**处理流程**：
1. 解析所有 `<!-- IMAGE_PLACEHOLDER -->` 标记
2. 按顺序匹配从 DOCX 提取的图片
3. 将占位符替换为简洁的图片引用（`![图片类型](路径)`）
4. 删除未使用的图片文件
5. 完整的长描述仅用于日志记录，不输出到文档

**优点**：
- ✅ 图片位置准确
- ✅ 输出简洁（仅保留图片类型）
- ✅ 自动清理冗余图片
- ✅ 处理速度快
- ✅ 可读性强（不冗余）

**错误处理**：
如果未找到占位符，系统将：
- ⚠️ 发出警告，提示可能的原因
- 📋 保留所有图片到文档末尾（避免数据丢失）
- 💡 建议检查提示词版本

转换完成后，`meta.json` 包含以下信息：

```json
{
  "input_file": "test.docx",
  "output_dir": "output_docx_to_md_v2/test",

  "math_formula_images": 2,
  "other_images": 3,
  "removed_images": 2,
  "processing_time": 45.67,
  "success": true

```

**字段说明**：
- `total_images`: 从 DOCX 提取的图片总数
- `math_formula_images`: 数学公式图片数量（占位符模式为 0）
- `other_images`: 保留的其他图片数量
- `removed_images`: 移除的图片数量
- `processing_time`: 处理耗时（秒）

## 占位符匹配规则

### 匹配优先级

1. **顺序匹配**：按占位符在文档中出现的顺序，依次匹配图片
2. **一一对应**：每个占位符匹配一张图片，不重复使用
3. **未处理图片**：多余的图片添加到文档末尾或删除

### 匹配示例

假设 DOCX 有 5 张图片，GLM 生成了 3 个占位符：

```
图片列表：[image1.png, image2.png, image3.png, image4.png, image5.png]
占位符：[占位符1, 占位符2, 占位符3]

匹配结果：
- 占位符1 → image1.png ✓
- 占位符2 → image2.png ✓
- 占位符3 → image3.png ✓
- image4.png → 添加到文档末尾或删除
- image5.png → 添加到文档末尾或删除
```

## 常见问题

### Q1: 为什么有些图片没有被匹配？

**A**: 可能的原因：
1. GLM 模型没有为该图片生成占位符
2. 图片数量多于占位符数量
3. 图片是纯数学公式（已被转为 LaTeX）

**解决方法**：检查生成的 Markdown，查看是否有未匹配的图片被添加到文档末尾。

---

### Q2: 占位符的描述不准确怎么办？

**A**:
1. 查看图片描述是否在文档中显示
2. 可以手动编辑 Markdown，修正图片描述
3. 图片文件本身是完整的，描述只是说明文字

---

### Q3: 如何禁用占位符功能？

**A**: 使用 `--no-analyze` 参数：

```bash
python3 scripts/convert_docx_to_markdown_v2.py input.docx --no-analyze
```

这样会跳过 GLM 占位符，直接插入所有图片到文档末尾。

---

### Q3: 如果没有占位符会怎样？

**A**: 系统会：
1. 显示警告信息
2. 保留所有图片到文档末尾（避免数据丢失）
3. 建议检查提示词版本是否为 v4

**这不是错误处理模式**，而是紧急备用方案，防止因GLM未生成占位符而导致图片完全丢失。

### Q4: 为什么不再使用 AI 分析模式？

**A**:
- **占位符模式更准确**：GLM理解上下文，位置精确
- **处理速度快**：不需要逐张调用AI分析
- **代码简洁**：减少依赖和维护成本
- **体验更好**：包含详细描述，便于阅读


- 忽略空格（`\s*`）
